# Комод — сайт салона интерьера

React + TypeScript + Vite, архитектура Feature-Sliced Design.
Каталог читает тестовые данные из кода или таблицу Google Sheets и фото с Google Диска (см. «Как подключить таблицу товаров и фото»).

## Запуск

```bash
cd komod-web          # cd — «change directory» («сменить каталог»): переходит в папку проекта
npm install           # npm — «Node Package Manager», install — «установить»: скачивает библиотеки из package.json в node_modules
npm run dev           # run — «запустить», dev — «development» («разработка»): поднимает локальный сервер, сайт откроется на http://localhost:5173
```

Остальные команды:

```bash
npm run build         # build — «собрать»: проверяет типы и собирает готовый сайт в папку dist
npm run typecheck     # typecheck — «проверка типов»: запускает TypeScript без сборки
npm run lint          # lint — «проверка кода»: ищет ошибки и сомнительные места через ESLint
npm test              # тесты разбора таблицы (Vitest)
```

## Структура (FSD)

Слои импортируют только то, что лежит ниже: `app → pages → widgets → features → entities → shared`.
У каждого слайса есть `index.ts` — публичный интерфейс, снаружи импортируем только через него.

| Слой | Что внутри |
|---|---|
| `app` | запуск приложения (`main.tsx`) и вход пререндера (`entry-server.tsx`), маршруты, общий каркас страниц, глобальные стили и цвета |
| `pages` | `home`, `catalog`, `product`, `solutions`, `solution`, `not-found` |
| `widgets` | крупные блоки: шапка, подвал, hero, готовые решения, комнаты, каталог, карточка товара, контакты и т. д. |
| `features` | `filter-products` (фильтры в адресной строке), `ask-in-whatsapp` (кнопки WhatsApp) |
| `entities` | `product`: типы, подписи, форматирование, загрузка данных, карточка и сетка; `solution`: готовое решение, загрузка данных и расчёт цены комплекта по товарам |
| `shared` | `config` (данные салона, маршруты, столбцы таблицы для сайта, размеры фото), `lib` (цена, ссылка WhatsApp, склонения), `ui` (кнопка, контейнер, секция, заголовок страницы `PageMeta`) |

## Что заменить перед запуском

- `src/shared/config/site.ts` — дни работы и выходные (часы уже настоящие). Номер WhatsApp, адрес и точка на карте уже настоящие.
- `src/entities/product/api/products.data.ts` и `src/entities/solution/api/solutions.data.ts` — тестовые товары и комплекты.
- `public/products/` — тестовые фото поставщика (на двух есть артикулы фабрики).
- `src/widgets/hero`, `showroom-info` — места с пометками TODO (фото шоурума).

## Как подключить таблицу товаров и фото

Сборка читает таблицу и папку с фото через API Google от имени сервисного аккаунта с правами только на чтение.
Публиковать таблицу в интернете не нужно (если она была опубликована, публикацию лучше снять).

1. [Google Cloud Console](https://console.cloud.google.com): создать проект, включить Google Sheets API и Google Drive API.
2. «IAM и администрирование → Сервисные аккаунты» → создать аккаунт (роли не нужны) → «Ключи» → «Добавить ключ» → JSON.
3. Поделиться таблицей и корневой папкой с фото с адресом сервисного аккаунта (`…@….iam.gserviceaccount.com`), права «Читатель».
4. Скопировать `.env.example` в `.env.local` (для `npm run dev` и `npm run build` на своём компьютере), вписать ID таблицы
   и папки, положить ключ в `google-key.json` в корне проекта (файл не попадает в git).
   На GitHub настройки задаются переменными и секретом репозитория (см. «Сборка и выкладка»).
   `VITE_DATA_SOURCE=sheets` включает таблицу, `mock` (по умолчанию) — тестовые данные из кода.
5. Сборка на `mock` проходит, но печатает жёлтое предупреждение. Неверное значение `VITE_DATA_SOURCE` или `sheets` без настроек Google — ошибка запуска.

Товары и фото удобнее заводить через админку на Apps Script (`admin/`, установка в `admin/README.md`).
Таблицу можно по-прежнему править и вручную.

Как читается таблица (`src/shared/lib/sheet`, `entities/*/api/*.sheet.ts`):

- Столбцы ищутся по заголовку до запятой или скобки («Цена, ₽» → «Цена»), порядок не важен.
- На сайт попадают только столбцы из `src/shared/config/sheet-columns.ts`: остальные (артикул поставщика, поставщик,
  дата проверки, «Актуальность», «Сумма товаров», любые новые внутренние) сборка выбрасывает до того, как данные окажутся в файлах сайта.
- «Гостиная», «Прованс», «Под заказ» переводятся в коды по словарям из `labels.ts`.
- Строка с ошибкой (пустой артикул, название, комната, стиль, наличие или состав комплекта; неизвестное значение;
  не число в цене, размерах или сроке; размеры заполнены частично; повторный артикул) пропускается.
  В режиме разработки причины видны в консоли браузера с номером строки таблицы.
- Пустые необязательные ячейки: числа и размеры — `null` («Цена по запросу»), текст — пустая строка.
- «На сайте: Нет» — товар скрыт: строка не попадает на сайт вовсе. Столбец добавляет админка; если его нет, показываются все товары.
- Фото товара — картинки из папки с его артикулом внутри корневой папки фото, по порядку имён (`KM-001_01.jpg`, `KM-001_02.jpg`…).
  Сборка пережимает их в WebP шириной 600 и 1600 px (`build/photos.ts`) и кладёт в `dist/photos/`; готовые файлы кэшируются в `.cache/photos`.
  Фото, которое не удалось прочитать (например, HEIC), пропускается с предупреждением.
  Если папки нет, берётся старый столбец «Ссылка на фото»: имя файла ищется в `public/products/`, ссылка `https://…` — как есть.
- Таблица и фото читаются только при сборке и встраиваются в сайт: посетители к Google не обращаются.
  Сайт пересобирается раз в час (см. «Сборка и выкладка»). При `npm run dev` таблица и фото читаются заново при каждом обновлении страницы.
- Пропущенные строки и фото видны в консоли браузера при разработке и в выводе `npm run build`.

## Сборка и выкладка

`npm run build` делает три шага (`vite.config.ts`, папка `build/`):

1. Читает таблицу и фото один раз (`build/catalog-source.ts`) и собирает сайт для браузера.
2. Собирает серверную версию (`src/app/entry-server.tsx`).
3. Пререндер (`build/prerender.ts`): каждая страница, товар и комплект становится готовым HTML
   (`dist/catalog/KM-001/index.html`), со своим заголовком и описанием для поисковиков. Плюс `dist/404.html`.

В браузере готовый HTML «оживает» (гидрация). Адреса с фильтрами (`/catalog/?room=living`) и адреса без готовой
страницы (новый товар до следующей сборки) отдаются как `404.html`, и сайт рисует нужную страницу сам.
Адреса страниц заканчиваются на `/` (`ROUTES` в `shared/config/routes.ts`), потому что каждая страница — папка с `index.html`.

Выкладка — `.github/workflows/deploy.yml`, раз в час и при каждом push в `main`. Сценарий сравнивает отпечаток
(коммит, время правки таблицы и список фото, `build/catalog-version.ts`) с файлом `deploy-hash.txt` в бакете и пересобирает сайт только при изменениях.
Кнопка «Run workflow» на вкладке Actions выкладывает сайт сразу. Если таблица недоступна или проверки не прошли,
сборка падает, а на хостинге остаётся прошлая версия.

Что настроить один раз:

- Yandex Cloud: бакет с публичным доступом на чтение объектов; вкладка «Веб-сайт» → «Хостинг»:
  главная страница `index.html`, страница ошибки `404.html`.
- Сервисный аккаунт с ролью `storage.editor` и статический ключ доступа.
- GitHub → Settings → Secrets and variables → Actions: секреты `YC_ACCESS_KEY_ID`, `YC_SECRET_ACCESS_KEY`,
  `GOOGLE_SERVICE_ACCOUNT_KEY` (содержимое JSON-ключа целиком); переменные `YC_BUCKET`, `GOOGLE_SHEET_ID`, `GOOGLE_PHOTOS_FOLDER_ID`.
  Старые переменные `PRODUCTS_CSV_URL` и `SOLUTIONS_CSV_URL` больше не нужны.

## Готовые решения

Комплект хранит только артикулы товаров. Сумма считается из цен каталога, а если у комплекта задана своя цена ниже суммы, сайт показывает выгоду.
Если у какого-то товара нет цены или он пропал из каталога, цена комплекта не выдумывается: показывается «Цена по запросу».
